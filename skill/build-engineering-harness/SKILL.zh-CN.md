# 构建工程 Harness

把软件仓库建设成人与 Agent 都能可靠工作的工程环境。将文档、规则、工具、验证和反馈视为产品的一部分，而不是事后补充。

评估项目前，先阅读 [references/personal-ai-engineering-playbook.md](references/personal-ai-engineering-playbook.md)。将其作为总体方法论，并按照下面的可执行流程工作。

当任务涉及仓库知识架构、文档治理、分层或作用域指令、事实来源冲突、文档漂移或 Agent 可导航性时，还应阅读 [references/repository-knowledge-governance.md](references/repository-knowledge-governance.md)。进行正式审计时，复制并按项目情况调整 [assets/repository-knowledge-audit-template.md](assets/repository-knowledge-audit-template.md)；如果用户只需要一个聚焦的问题判断或建议，不要强行套用完整模板。

> 本文件是供团队成员阅读的中文版。Codex 实际加载的入口仍是同目录下的 `SKILL.md`。

## 选择执行模式

如果用户要求评估、搭建或改进项目，使用**工程 Harness 模式**，并遵循下面的两阶段确认机制。

如果用户明确要求对已完成项目进行收尾、复盘、经验总结或生成新人上手文档，使用**项目收尾模式**。该模式固定创建或更新：

- `docs/project-retrospective.md`
- `docs/project-onboarding.md`

用户明确调用项目收尾模式，即表示授权仅写入这两份文档。除非无法发现必需事实，或更新已有文件会丢失相互冲突的人工内容，否则无需再进行一次方案确认。

## 执行约定

在工程 Harness 模式下，严格区分两个阶段：

1. 检查并提出方案，不修改项目。
2. 只有在用户明确批准方案后才实施。

不要把用户最初提出的“评估”“准备”“建立”或“改进”工程 Harness 理解为写入许可。完成第一阶段后，提交具体方案并等待用户确认。

遵守仓库已有的指令和约定。保留与当前任务无关的用户改动，不要仅仅为了采用偏好的文件名而替换内容完善的现有文档。

## 第一阶段：检查并提出方案

以只读方式检查仓库。查找项目约束说明、文档、源码布局、构建配置、测试、自动化、版本控制状态和现有验证命令。能够从仓库发现的事实，应自行查明，不要询问用户。

判断项目属于普通软件项目，还是包含 AI 或 Agent 组件的项目。识别：

- 项目目标、目标用户、输入、输出和可衡量的成功标准；
- 架构边界、数据流、API 和核心组件；
- 已存在的仓库知识及其存放位置；
- 开发和发布工作流；
- 人、Agent 与自动化当前的职责分工；
- 已有的测试、评估、日志、错误处理和反馈闭环；
- 应沉淀为可复用文档、模板或自动化的知识。

如果项目包含 AI 或 Agent 组件，额外检查：

- Prompt 的清晰度和版本管理；
- Context 的来源、选择机制、时效性和容量限制；
- Tool 的输入、输出、权限和错误行为；
- 输出 Schema 和下游验证；
- Memory 的作用范围、保留策略、隐私和陈旧状态风险；
- 失败处理、重试、降级方案和可观测性；
- Accuracy、Latency、Cost 和 Reliability 的评估覆盖情况。

如果无法从仓库确定关键意图，每次只询问一个聚焦的决策问题，并同时给出推荐答案。

第一阶段应提交一份包含以下内容的方案：

1. **项目理解**——当前用途、用户、输入、输出、架构和重要假设。
2. **Harness 资产清单**——已经存在并应保留的内容。
3. **缺口与风险**——根据影响程度排序，并提供仓库文件证据。
4. **拟议改动**——计划创建或更新的确切文件，以及每项改动的简要说明。
5. **验证计划**——要执行的命令、测试和评估，以及预期的成功证据。
6. **支撑性代码改动**——单独列出拟议的小型产品代码改动，说明影响范围及其保持行为不变的理由。
7. **待决事项**——必须由用户决定的未解决问题。

等待用户明确批准。如果用户只批准部分方案，只实施获批部分。

## 第二阶段：实施已批准的方案

优先更新有价值的现有文件，不要创建内容重复的平行文档。只有当必要知识没有合适的存放位置时，才创建新文件。文件名和位置应适应仓库现有约定，不要机械地创建一套固定文档。

根据项目需要，确保最终形成的项目知识覆盖：

- 项目用途、用户、输入、输出和可衡量的成功标准；
- 架构、模块边界、数据流、接口和重要决策；
- 环境准备、开发、测试、调试和发布流程；
- 人与 Agent 的职责以及安全交接点；
- 常见故障、排查方式和已知约束；
- 验证流程以及如何解释验证结果；
- 可复用的模板、自动化和经验教训。

让文档靠近其约束的代码或配置。使用明确的模块名称和职责，避免模糊的万能结构。

## 项目收尾模式

写入任何收尾文档前，先阅读 [references/project-closeout-templates.md](references/project-closeout-templates.md)。

### 收集证据

检查仓库指令、现有文档、依赖清单、源码布局、关键入口、测试、构建与部署配置、版本控制历史以及当前工作区状态。以源码和实际验证结果为证据，不要把计划或过期文档当作已经交付的功能。

能够从项目中查明的事实应自行查明。如果项目原始目标等关键信息确实无法恢复，只询问一个聚焦问题。对于非关键未知信息，应明确标为未知，不得编造。

不要泄露密钥、个人数据、凭据或敏感环境变量值。只有必要时才记录配置变量名称。

### 验证最终状态

在成本和副作用合理的情况下，运行已有且安全的构建、测试、Lint 或评估命令。未经单独授权，不要运行破坏性命令、生产环境命令、部署、迁移或付费评估。

明确区分：

- 已实现且已经验证的行为；
- 已实现但尚未验证的行为；
- 仍处于计划中或尚未完成的行为。

没有真实命令证据时，不得声称验证通过。

### 写入固定文件

如果需要，创建 `docs/` 目录。在同一次收尾中创建或更新以下两个文件：

1. `docs/project-retrospective.md`
2. `docs/project-onboarding.md`

使用用户要求的语言；如果用户没有指定，则采用项目现有维护文档的主要语言。目标文件已经存在时，保留准确的人工知识并更新过期章节，不要整份覆盖。

引用仓库文件时使用相对路径。确保两份文档脱离当前对话后仍然有用；对于其他地方已经维护的长篇内容，应链接到事实来源，避免重复。

在项目收尾模式下，不要修改产品代码、测试、配置、依赖或其他项目文档，除非用户另行提出要求。

### 检查文档质量

结束前：

- 确认两份固定文件都存在；
- 确认模板要求的所有章节都已包含；
- 在可行范围内验证命令和文件链接；
- 交叉核对两份文档中的目标、架构、关键入口和验证状态；
- 删除空泛经验、无证据结论、占位符和意外泄露的敏感信息。

最后报告两份文件路径、实际执行的检查、仍未知的信息和证据限制。

## 产品代码边界

本节只适用于工程 Harness 模式。项目收尾模式只能修改两份收尾文档。

不要实现新的业务功能，也不要进行大规模架构重写。

只有同时满足以下条件，才可以修改支撑性产品代码：

- 该改动已列入用户批准的第一阶段方案；
- 保持预期业务行为不变；
- 不改变公开 API、数据库 Schema 或外部协议；
- 不新增生产依赖；
- 影响范围局部、可解释且可测试。

允许的支撑性改动包括：

- 改善含义模糊的命名；
- 按照已有职责拆分明显过大的函数、类或文件；
- 补充日志、错误处理、类型信息或输入校验；
- 进行改善可测试性的局部调整。

如果不能确信影响范围或行为是否保持不变，只提供建议，不要修改代码。

## 建立可执行验证

先运行已有的相关检查。只添加经过用户批准的测试、评估脚本、Fixture 或最小验证配置。

根据项目风险，覆盖正常行为、重要边界和失败路径。对于 AI 或 Agent 系统，在适用时采用可衡量的 Accuracy、Latency、Cost 和 Reliability 评估。

不要仅凭代码检查就宣称功能可用。记录实际执行的检查，区分已通过和未运行的项目，并说明任何环境限制或剩余缺口。

## 闭合反馈循环

第二阶段结束时，说明：

- 创建或修改了哪些文件；
- 验证证据和结果；
- 尚未解决的风险或决策；
- 产出了哪些可复用资产；
- 哪些经验值得写入现有项目知识；
- 下一轮最小且有价值的改进。

保持 Harness 与项目规模相称。优先维护小而准确的单一事实来源，避免建立大量容易过期的文档。
